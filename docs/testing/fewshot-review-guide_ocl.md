ฉบับ 23 ต.ค. 2569 · ไฟล์ที่ต้องตรวจอยู่ที่ `apps/api/src/ocl_api/fewshot/` (`info.json`, `plo.json`, `courses.json`) · ตัวอย่างทั้งหมดเริ่มต้นสถานะ `draft`

## 1. few-shot คืออะไร และทำไมต้องตรวจละเอียด

few-shot คือ "ตัวอย่างโจทย์พร้อมเฉลย" ที่ระบบส่งให้แบบจำลอง (Gemma หรือ Gemini) ดูก่อนสกัดข้อมูลเล่มจริง แบบจำลองจะเลียนแบบเฉลยนั้นทั้งรูปแบบและวิธีคิด

ดังนั้น **ถ้าเฉลยผิด 1 ค่า ความผิดนั้นจะถูกเลียนแบบในทุกเล่มที่นำเข้าหลังจากนั้น** การตรวจจึงต้องละเอียดกว่าการตรวจผลสกัดทั่วไป

ระบบจะส่งเฉพาะตัวอย่างที่ผ่านการอนุมัติ (`approved`) และจะไม่ส่งตัวอย่างของเล่มเดียวกับเล่มที่กำลังนำเข้า (กันไม่ให้ระบบ "จำเฉลยของตัวเอง")

| ส่วน | ไฟล์ | ตัวอย่างที่มี | สิ่งที่ตัวอย่างสอน |
|---|---|---|---|
| ข้อมูลหลัก | `info.json` | info-01 (วท.บ. ภูมิอากาศ), info-02 (วท.บ. อาหาร PDF) | แปลงจำนวนในข้อความเป็นตัวเลข และตอบ null เมื่อเล่มไม่ระบุค่าจริง |
| PLO | `plo.json` | plo-01 (ศศ.ม. 2 แผน), plo-02 (วท.บ. ภูมิอากาศ แผนเดียว) | แยก PLO ตามแผนการศึกษา และรวมข้อความที่ขึ้นบรรทัดใหม่กลางประโยค |
| รายวิชา | `courses.json` | courses-01, courses-02 · **สถานะ rejected ไม่ต้องตรวจรอบนี้** | ผลวัด 23 ต.ค. พบว่าตัวอย่างรายวิชาทำให้ Gemini ตอบรายวิชาน้อยลงมาก (57 → 16 รายวิชา) จึงปิดไว้จนกว่าจะออกแบบใหม่ (เหตุผลอยู่ในช่อง review_notes) |

รอบนี้ตรวจ 4 ตัวอย่าง (info-01, info-02, plo-01, plo-02) ใช้เวลาประมาณ 20–30 นาทีต่อตัวอย่าง รวมราว 1.5–2 ชั่วโมง

ผลวัดเบื้องต้น (23 ต.ค., `docs/eval/run-2026-10-23-fewshot/summary.md`): ตัวอย่างข้อมูลหลักทำให้ Gemma ตอบฟิลด์ตัวเลขได้ครบ (6/10 → 10/10 และ 7/11 → 11/11) การตรวจตัวอย่างชุดนี้ให้ถูกต้องจึงมีผลต่อคุณภาพจริง

## 3. โครงสร้างของตัวอย่าง 1 รายการ

```json
{
  "id": "info-01",
  "status": "draft",
  "source": { "book": "วท.บ. วิทยาการการเปลี่ยนแปลงสภาพภูมิอากาศ.docx", "chapter": "หมวด 1", "pages": [5, 11] },
  "teaches": "แปลงจำนวนในข้อความเป็นตัวเลข ... และตอบ null เมื่อเล่มไม่ระบุค่าจริง",
  "input": "จากหมวดที่ 1 ด้านล่าง ให้ค่าของฟิลด์: ...\n\nรหัสหลักสูตร xxxxxxxxxxxxx\n...",
  "output": { "program_code": null, "total_credits": 127, "start_year": 2569, "...": "..." },
  "evidence": { "total_credits": { "page": 5, "snippet": "ไม่น้อยกว่า 127 หน่วยกิต" } },
  "reviewed_by": null,
  "reviewed_at": null,
  "review_notes": ""
}
```

| ช่อง | ความหมาย | ผู้ตรวจแก้ได้ไหม |
|---|---|---|
| `id` | รหัสตัวอย่าง | ไม่ได้ |
| `status` | `draft` รอตรวจ · `approved` อนุมัติ · `rejected` ไม่ผ่าน | **แก้** |
| `source.book` / `pages` | เล่มและหน้าที่ตัดข้อความมา | ไม่ได้ (ถ้าผิด ให้เขียนใน `review_notes`) |
| `teaches` | ตัวอย่างนี้ตั้งใจสอนอะไร | ไม่ได้ |
| `input` | ข้อความที่ส่งให้แบบจำลอง ต้องเหมือนที่ระบบส่งจริงทุกตัวอักษร | **ห้ามแก้** |
| `output` | เฉลย | แก้ได้เฉพาะตามข้อ 5.3 |
| `evidence` | หน้าและข้อความที่เป็นหลักฐานของแต่ละค่า (มีเฉพาะ info) | ไม่ได้ |
| `reviewed_by` | ชื่อผู้ตรวจ | **กรอก** |
| `reviewed_at` | วันที่ตรวจ รูปแบบ ค.ศ. `2026-10-24` | **กรอก** |
| `review_notes` | ข้อสังเกต สิ่งที่แก้ เหตุผลที่ปฏิเสธ | **กรอก** |

## 5. ขั้นตอนตรวจต่อ 1 ตัวอย่าง

### 5.1 ตรวจ input กับเล่มจริง

1. ไปหน้าที่ระบุใน `source.pages` ของเล่ม
2. อ่าน `input` ทีละบรรทัด (ข้ามบรรทัดคำสั่งด้านบนสุดที่ขึ้นต้นว่า "จากหมวดที่ 1…", "สกัดรายการ PLO…" หรือ "จากข้อความต่อไปนี้…" ซึ่งเป็นคำสั่งของระบบ)
3. ข้อความต้องตรงกับเล่มตามลำดับ ไม่มีคำเกินหรือหาย **ยกเว้น** การขึ้นบรรทัดและช่องว่างที่ต่างได้
4. input อาจถูกตัดท้ายกลางเนื้อหาได้ (เพื่อให้สั้น) ถือว่าปกติ ตราบใดที่ค่าทุกค่าใน `output` อยู่ก่อนจุดที่ตัด
5. ถ้า input ไม่ตรงกับเล่ม (เช่น สระหาย ตัวเลขผิด คำเกิน) ห้ามแก้เอง ให้ตั้ง `rejected` และเปิด issue ประเภท "ข้อมูลสกัดผิด" เพราะแปลว่าการแปลงไฟล์ของระบบมีปัญหา

### 5.2 ตรวจ output ทีละค่า

**ข้อมูลหลัก (info)** ตรวจทั้ง 11 ฟิลด์

| ฟิลด์ | ตรวจอะไร |
|---|---|
| `program_code` | รหัส สกอ. 14 หลัก ถ้าเล่มเขียน xxxx หรือเว้นว่าง ต้องเป็น `null` |
| `name_th`, `name_en` | ชื่อหลักสูตรเต็มตามเล่ม ตรงทุกตัวอักษร |
| `degree_full_th`, `degree_abbr_th`, `degree_full_en`, `degree_abbr_en` | ชื่อปริญญาเต็ม/ย่อ ไทย/อังกฤษ รวมวงเล็บสาขา |
| `total_credits` | ตัวเลขล้วน เช่น `127` (ไม่มีเครื่องหมายคำพูด ไม่มีคำว่า "หน่วยกิต") |
| `duration_years` | ระยะเวลาศึกษาตามหลักสูตร (ปี) เป็นตัวเลข |
| `start_semester`, `start_year` | ภาคการศึกษาและปีการศึกษา (พ.ศ.) ที่เริ่มใช้หลักสูตร เป็นตัวเลข |

**PLO (plo)**
- จำนวน PLO ใน output ต้องเท่ากับจำนวน PLO ใน input ทุกแผน
- `code` ต้องเป็นรหัสล้วน เช่น `PLO1` ห้ามมีชื่อแผนปน
- `plan` ต้องเป็นชื่อแผนตามหัวข้อในเล่ม (เช่น `แผน 1 แบบวิชาการ`) ถ้าเล่มมี PLO ชุดเดียว ต้องเป็น `null` ทุกข้อ
- `text` ต้องเป็นข้อความ PLO เต็ม รวมส่วนที่ขึ้นบรรทัดใหม่ (เช่น "...เครื่องมือเชิงเศรษฐศาสตร์" + "ในการศึกษาประเด็น...ได้อย่างมีประสิทธิภาพ" = ข้อความเดียว)
- PLO ของแผน 1 และแผน 2 ที่รหัสเดียวกันต้องมีข้อความตามแผนของตัวเอง ห้ามสลับ

**รายวิชา (courses)** (สำหรับตัวอย่างรายวิชาที่ออกแบบใหม่ในรอบถัดไป)
- **ทุกรหัสวิชาที่ปรากฏใน input ต้องอยู่ใน output** นี่คือบทเรียนหลักของตัวอย่างนี้ (กันแบบจำลองข้ามรายวิชา) ให้ใช้ค้นหา (Ctrl/Cmd+F) รหัสวิชาใน input แล้วนับเทียบ
- `code_th`, `name_th`, `code_en`, `name_en`, `credit_text` ตรงทุกตัวอักษร หน่วยกิตแบบ `3(3-0-6)` ตรงทั้ง 4 ตัวเลข
- ไม่มีคำอธิบายรายวิชาใน output (คำสั่งบอกว่าไม่ต้องใส่)
- รายวิชาที่ถูกตัดครึ่งท้าย input (มีรหัสแต่ไม่มีชื่อครบ) ต้องไม่อยู่ใน output

### 5.3 ถ้าเจอค่าใน output ผิด

| สถานการณ์ | ทำอย่างไร |
|---|---|
| ค่าที่ถูกต้อง **ปรากฏใน input** (เช่น ชื่อวิชาสะกดผิดใน output แต่ input ถูก) | แก้ใน `output` ได้ แล้วเขียนใน `review_notes` ว่า "แก้ <ฟิลด์>: <ค่าเดิม> → <ค่าใหม่>" |
| ค่าที่ถูกต้อง **ไม่อยู่ใน input** (เช่น input ถูกตัดก่อนถึงค่านั้น) | ห้ามเพิ่ม ตั้ง `rejected` เขียนเหตุผล ให้ผู้พัฒนาสร้าง input ใหม่ |
| ไม่แน่ใจว่าค่าไหนถูก | คง `draft` เขียนคำถามใน `review_notes` แล้วแจ้ง PM |

กฎสำคัญ: แบบจำลองถูกสอนให้ "คัดลอกจากข้อความ" ดังนั้นทุกค่าใน output ต้องอ่านเจอใน input ตัวตรวจอัตโนมัติ (ข้อ 6) จะฟ้อง ERROR ถ้าไม่เป็นเช่นนั้น

### 5.4 ตรวจข้อมูลส่วนบุคคล

ตัวอย่างต้องไม่มีชื่อ-นามสกุลบุคคล เลขบัตร อีเมล หรือเบอร์โทร ถ้าพบ ให้ตั้ง `rejected` (ชุดแรกไม่มีส่วนอาจารย์ จึงไม่ควรพบ)

### 5.5 กำหนดสถานะ

| สถานะ | ใช้เมื่อ |
|---|---|
| `approved` | input ตรงเล่ม ทุกค่าใน output ถูกต้องและครบ ไม่มีข้อมูลส่วนบุคคล และ `teaches` ตรงกับสิ่งที่ตัวอย่างแสดงจริง |
| `rejected` | input ไม่ตรงเล่ม หรือ output ผิดแบบที่แก้ตามข้อ 5.3 ไม่ได้ หรือพบข้อมูลส่วนบุคคล (ต้องเขียนเหตุผล) |
| `draft` | ยังตรวจไม่เสร็จ หรือรอ PM ตัดสิน |

เมื่อเปลี่ยนเป็น `approved` ต้องกรอก `reviewed_by` และ `reviewed_at` ทุกครั้ง

## 6. รันตัวตรวจอัตโนมัติ

ผู้ที่มีเครื่องพัฒนา (มี `uv` และ repo) รันคำสั่งนี้หลังแก้ไฟล์ทุกครั้ง ถ้าผู้ตรวจไม่มีเครื่องพัฒนา ให้ส่งไฟล์ที่แก้ให้ผู้พัฒนาหรือ PM รันให้

```bash
cd "/Users/kanabadeedii/PycharmProjects/OCL agent" && uv run ocl fewshot check
```

ตรวจเฉพาะส่วน: `uv run ocl fewshot check plo`

| ผล | ความหมาย | ทำอย่างไร |
|---|---|---|
| `OK info/info-01 (approved)` | ตัวอย่างผ่านทุกเงื่อนไข | – |
| `WARN …` | ควรดู แต่ใช้งานได้ เช่น input ยาวเกิน 3,000 ตัวอักษร ยังไม่มีตัวอย่างที่ approved หรือ input มีรหัสที่ output ไม่ได้ตอบ | อ่านข้อความแล้วตัดสินใจ ถ้าเป็นรหัสวิชาจริงที่ตกหล่น ต้องแก้ |
| `ERROR …` | ใช้ไม่ได้ เช่น JSON เสีย approved แต่ไม่มีผู้ตรวจ ค่าใน output ไม่อยู่ใน input รหัส PLO มีชื่อแผนปน | ต้องแก้ก่อนส่ง |

ตัวอย่างข้อความ ERROR และความหมาย:

```text
ERROR plo/plo-01: PLO ลำดับ 4: code 'PLO1 แผน 2' ต้องเป็นรหัสล้วน เช่น PLO1 (ชื่อแผนให้ใส่ในช่อง plan)
ERROR info/info-02: total_credits = 130 ไม่พบตัวเลขนี้ใน input
ERROR courses/courses-01: approved แต่ reviewed_at ไม่ใช่วันที่รูปแบบ ปปปป-ดด-วว (ค.ศ.)
ERROR plo: plo.json ไม่ใช่ JSON ที่ถูกต้อง: บรรทัด 41 คอลัมน์ 7 (Expecting ',' delimiter)
```

ข้อผิดพลาด JSON ที่พบบ่อยเวลาแก้ด้วยมือ: ลืมเครื่องหมายจุลภาค `,` ระหว่างช่อง ใช้เครื่องหมายคำพูดแบบโค้ง “ ” แทน " และพิมพ์ `null` เป็น `"null"` (มีเครื่องหมายคำพูด)

## 7. ตัวอย่างการตรวจจริง: info-01

1. เปิด `วท.บ. วิทยาการการเปลี่ยนแปลงสภาพภูมิอากาศ.docx` หน้า 5 และหน้า 11
2. input บรรทัด "รหัสหลักสูตร xxxxxxxxxxxxx" ตรงกับหน้า 5 → `program_code` ต้องเป็น `null` ✓
3. input มี "ไม่น้อยกว่า 127 หน่วยกิต" ตรงกับหน้า 5 ข้อ 4 → `total_credits: 127` ✓ (ตัวเลข ไม่ใช่ข้อความ)
4. input มี "เริ่มใช้หลักสูตรนี้ ในภาคการศึกษา 1 ของปีการศึกษา 2569" ตรงกับหน้า 11 → `start_semester: 1`, `start_year: 2569` ✓
5. เทียบชื่อหลักสูตรและชื่อปริญญา 6 ฟิลด์กับหน้า 5 ทีละตัวอักษร ✓
6. input มีช่องเลือก "□ 2 ปี ☑ 4 ปี □ 5 ปี □ 6 ปี" ตรงกับหน้า 5 ช่องที่ถูกเลือกคือ 4 ปี → `duration_years: 4` ✓ (ตรวจว่าเป็นช่องที่มีเครื่องหมายถูก ☑ ไม่ใช่ช่องแรกที่เห็น)
7. ไม่มีข้อมูลส่วนบุคคล ✓
8. แก้ไฟล์:

```json
"status": "approved",
"reviewed_by": "สมชาย ใจดี",
"reviewed_at": "2026-10-24",
"review_notes": "ตรวจครบ 11 ฟิลด์กับหน้า 5 และ 11"
```

## 10. คำถามที่พบบ่อย

**ทำไมห้ามแก้ input** input ต้องเหมือนสิ่งที่ระบบส่งจริง ถ้าแก้ให้สวย แบบจำลองจะเรียนจากข้อความที่ไม่เคยเจอในงานจริง

**ทำไม output ต้องอ่านเจอใน input** แบบจำลองถูกสั่งให้คัดลอกจากต้นฉบับและห้ามแต่งเพิ่ม ถ้าเฉลยมีค่าที่ไม่อยู่ในข้อความ จะสอนให้แบบจำลองเดาค่า

**ตัวอย่างที่ rejected แล้วทำอย่างไรต่อ** ผู้พัฒนาสร้างตัวอย่างใหม่ด้วย id ใหม่ (เช่น info-03) แล้วส่งตรวจรอบใหม่ ตัวอย่างเดิมคงไว้เป็นประวัติ ระบบไม่ส่งตัวอย่างที่ rejected

**เพิ่มตัวอย่างจากเล่มอื่นได้ไหม** ได้ แต่ต้องเป็นเล่มที่ผ่านหมวด V ของรอบทดสอบแล้ว และให้ผู้พัฒนาสร้างจากระบบ (ไม่พิมพ์ input เอง) เพื่อให้ input เหมือนงานจริง

**ส่งตัวอย่างได้กี่ตัวต่อครั้ง** ระบบส่งไม่เกิน 2 ตัวอย่างต่อส่วนต่อคำขอ ตัวอย่างที่อยู่ก่อนในไฟล์จะถูกเลือกก่อน
